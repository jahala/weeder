# bite — what the proof repository had to say

bite does not ship: 0 of the 18 nodes this repository was built from asked for
phases, and the conductor that ran them commits a node once, so no node in the
proof repository leaves a test commit bite could apply on its own. The bar was
90 percent of phased nodes yielding a clean test commit. The measurement is 0 of
0, `weeder --help` does not print `bite`, and `garden.json` declares the five
faces it does print.

`scripts/check/bite-kill.sh` is the check that holds this file to the tree. It
counts the nodes out of `plans/` and the commits out of git, recomputes every
row and the totals, and then holds the consequence to the number in both
directions: over the bar the binary has to offer the face, under it the binary
must not.

## What the proof repository is

weeder is built by pleach, node by node, and both halves of that leave a record
here. `plans/` carries the work orders the conductor was given, one file per
wave, each naming its nodes and the shape of work each node was asked for.
The history carries what came back: a settled node lands one commit, subject
`pleach: <id> verified (done)`, and a node whose work was preserved rather than
landed carries `quarantined` in the same place.

Those two are the ground truth. The plans say which nodes asked for phases; the
commits say what those nodes left behind. Neither can be edited by writing prose
in this file, which is the point of measuring against them.

The node ids and plan filenames in the table read `weed`, because that is the
name the project carried while it was being built and the work orders and commit
subjects say so. The tool is weeder now; the record of how it was made is not
rewritten to agree.

## What a clean test commit is

pleach's phased work shape is `{test, phases}`: a node names the command that
runs its tests and a list of `red`, `impl` and `green` prompts. bite needs that
red phase to be a commit of its own, so it can put the tests on the base without
the implementation under them and watch the command fail.

A node yields a clean test commit when the commits it landed carry the tests
apart from the implementation: a commit whose changed files are all tests, with
the implementation in the commit above it. A node whose one commit carries test
files and production files together yields none, because applying the tests
alone from it would mean splitting a commit, and bite splits nothing.

## Why there are none

The plans ask for `{prompt}` nodes. `tend2 emit-plan` writes one prompt per
loop, carrying the loop's checks and its Tried lines, and every wave the
conductor emitted for weeder came out that way. No plan in `plans/` names a
`phases` array.

The deeper reason is the one that decides the kill: pleach 0.0.1 commits a node
once, whatever its phases were. `src/loop/run-work.ts` walks the phases by
sending each prompt into the same worker session and running the node's `test`
command after the red phase, where it has to fail, and after the green phase,
where it has to pass. The commit comes later and elsewhere: `src/loop/run-plan.ts`
commits the node's whole staged tree at close, once, on `node/<id>`, in the
commit-before-emit step. A phased node therefore lands the tests and the
implementation in one commit, and bite has nothing to apply alone. Running the
proof repository's waves again as phased nodes would not change the count,
because this conductor cannot produce the shape bite needs.

The history shows it plainly. Of the 33 node commits in it, 25 change test files
and production files together and 8 carry production files alone; not one
carries tests by themselves. `rules-tests` landed 136 test files beside 156
others in a single commit, and the smallest mixed commit, `calibration`, still
carried 3 test files beside 7.

## The kill, and what is in the tree

The face is built and proven, and the binary does not offer it.

- `weeder --help` does not print `bite`; the subcommand is hidden in
  `src/main.rs`, with the reason on the line above it.
- `garden.json` declares `check`, `scan`, `guard`, `hook` and `rules`, and
  `tests/garden_manifest.rs` holds that list equal to what the binary prints.
- `SKILL.md` teaches the faces weeder offers, so it does not teach `bite`.
- B1 stays in the catalogue, at block level, and `docs/rules.md` says under it
  that the face is unshipped. The rule is in the binary; `weeder rules` tells the
  truth about the binary.
- `src/faces/bite.rs`, `src/core/bite.rs`, `src/core/rules/bite/b1.rs`,
  `tests/bite.rs` and `tests/bite_exec.rs` stay, and run in CI with everything
  else. A face nobody can run is a face nobody can measure, and this file exists
  to be measured again.

## What would turn it on

A conductor that commits the red phase before it sends the impl prompt. The
commit needs nothing else in it: the tests as the worker left them, on the
node's base. Then:

1. Run `bash scripts/check/bite-kill.sh`. It recounts from `plans/` and the
   commits, and refuses this file if the numbers moved.
2. At 90 percent or over, take `hide` off `Command::Bite` in `src/main.rs`, add
   `bite` to `faces` in `garden.json`, and name the subcommand and its flags in
   `SKILL.md`, which `tests/skill_md.rs` will then require.
3. `tests/bite.rs` and `tests/bite_exec.rs` already hold the behaviour: a test
   that fails alone and passes with the change is clean, one that passes alone
   is B1 at block level naming the cases it added, a command that hangs is exit
   3 with the deadline named, and the worktree is gone on every path.
